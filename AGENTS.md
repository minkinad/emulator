# Инструкции для агентов

## Назначение и текущее состояние

Проект — учебный эмулятор процессора по материалам `task/task.md`. В репозитории находятся задание, документация, сайт на VitePress и GitHub Actions. Стек — TypeScript + React + Vite. Завершены этапы 3–5: независимое ядро CPU в `src/core/` и ассемблер в `src/assembler/`. React-интерфейс находится в `src/ui/`, модель сеанса без DOM — в `src/ui/model/`. Следующий этап — интеграция программ массивов.

Пользователь работает в команде из трёх разработчиков. **Назначен вариант 7:** трёхадресные команды, гарвардская архитектура, знаковые целые в дополнительном коде, сумма элементов массива и свёртка двух массивов по 10 элементов с длинной арифметикой. Сравнение других вариантов в `docs/reference/variants.md` — справочная информация. Ядро и ассемблер реализуются на TypeScript независимо от React; React + Vite используются для интерфейса эмулятора.

## Перед изменениями

- Прочитать `README.md`, относящийся к задаче раздел `task/task.md` и при работе над машиной — `docs/architecture/cpu.md` и `docs/architecture/programs.md`. Сравнение архитектур — в `docs/reference/variants.md`.
- Проверить `git status --short`; сохранять чужие и незакоммиченные изменения.
- Исходные файлы `task/` считать материалами задания. Изменять их только при явной задаче на исправление исходных материалов; выявленные расхождения записывать в документации.
- Не редактировать внутренние файлы `.git/` вручную. Использовать штатные команды Git; не делать разрушительные сбросы и очистку без явного поручения.
- Писать документацию, объяснения и сообщения об ошибках по-русски. Имена программных сущностей выбирать последовательно в рамках выбранного языка.

## Ограничения задания

- Архитектура памяти, адресность, знаковость и длина свёртки закреплены вариантом 7. Проектные решения закреплены в `docs/architecture/cpu.md`: 16-битные данные, 16 РОН, 32-битные инструкции, 1024 ячейки команд и 4096 ячеек данных; сумма 32-битная, свёртка 48-битная.
- Память команд и память данных раздельны: одинаковые числовые адреса в них обозначают разные ячейки. В арифметической трёхадресной команде получатель и два источника задаются явно.
- Инструкции имеют фиксированную длину, работают со скалярами; доступ к ОЗУ осуществляется через пересылку и обмен.
- Для адресных машин нужны непосредственная, прямая, регистровая и косвенно-регистровая адресации. Для безадресной машины учитывать исключения раздела 4.1.
- Программы пользователя проходят путь «ассемблер → машинные слова → память → декодирование → исполнение». Не подменять CPU непосредственным исполнением исходных строк.
- Обработка массивов выполняется в цикле внутри эмулируемой программы. Вторая программа обязательно использует длинную арифметику.
- После каждой команды доступны состояния обязательных компонентов. Текущая инструкция отображается как машинное слово, ассемблер и поля.
- Отчёт должен описывать фактическую реализацию и содержать обе программы на ассемблере и в машинных кодах.

## Архитектура реализации

- Отделять ядро, ассемблер и интерфейс. Ядро не зависит от UI и выполняет ровно одну инструкцию через `step()`.
- Следовать контракту `docs/architecture/cpu.md`; `docs/architecture/programs.md` содержит алгоритмические листинги: сборка и адреса переходов проверяются тестами; полная интеграционная проверка массивов остаётся этапом 6. При изменении контракта синхронно обновлять реализацию, документацию и контрольные примеры.
- Хранить правила кодирования и семантику команд согласованно для ассемблера, декодера, интерфейса и документации.
- Явно определить единицу адресации, разрядность данных, длину инструкции, шаг `PC`, порядок частей длинных чисел и изменение флагов.
- Моделировать ограниченную разрядность. Не путать перенос с переполнением знакового числа; не полагаться на поведение числового типа языка без проверки.
- Для длинной знаковой арифметики расширять знак произведения до ширины накопителя; проверять отрицательные значения, смешанные знаки, минимум диапазона и переносы между словами.
- Широкие типы языка допустимы внутри модели и эталонных проверок, но не заменяют последовательность операций длинной арифметики виртуального процессора.
- Предусмотреть остановку, лимит исполнения и понятные ошибки памяти, команд и стека, если он используется.
- Реализовывать один выбранный вариант. Расширения из раздела 4.2 добавлять по отдельной задаче или требованию преподавателя.

## Проверки и документация

- Работать по этапам из `docs/project/implementation.md`. По завершении каждого этапа обновить его статус и CHANGELOG, сделать точечные коммиты в `main`, отчитаться в чат и запросить продолжение. Следующий этап начинать только после ответа пользователя; это явное требование пользователя.
- Оформление документации вдохновлено SwiftUI. Сайт остаётся на VitePress, а приложение реализуется на согласованном TypeScript + React + Vite.
- Нужен Node.js 22.12+. Установка — `npm ci`; ядро: `npm run typecheck`, `npm test`, `npm run build`, `npm run core:demo`, `npm run assembler:demo`. Типы, модульные проверки и сборки: `npm run check`. Приложение: `npm run dev`, `npm run app:build`, `npm run preview`. Браузерные сценарии: `npx playwright install chromium`, затем `npm run test:browser` после сборки приложения. Сайт: `npm run docs:dev`, `npm run docs:build`, `npm run docs:preview`. Не выдавать сайт за интерфейс эмулятора.
- После изменений сайта выполнять `npm run docs:build`, проверять навигацию, поиск, светлую/тёмную темы и мобильную вёрстку при изменении оформления. Полный артефакт сайта и приложения собирается через `npm run site:build`. Публикация выполняется `.github/workflows/pages.yml` из `main`; в pull request — только сборка.
- Публичная документация описывает продукт без назначенного номера варианта, персональных подсказок команде и диалоговой истории. Разбор всех вариантов сохраняется как справочник. Рабочие инструкции и порядок этапов остаются здесь; AGENTS.md не публикуется на сайте.
- Исходники страниц — README, CHANGELOG, `docs/` и `.github/CONTRIBUTING.md`. Каталоги `website/guide/` и `website/project/` генерируются; редактировать и коммитить их не нужно. Главная и тема находятся в `website/`.
- Структура описана в `docs/project/structure.md`: исходники — `src/`, тесты — `tests/`, машинные примеры — `examples/machine/`, ассемблерные — `examples/assembly/`. Документация разделена на `docs/architecture/`, `docs/project/`, `docs/reference/`; подготовка сайта — `scripts/docs/prepare.mjs`. При переносе файлов сохранять адреса страниц и обновлять относительные ссылки, CI и инструкции.
- При изменении ассемблера и добавлении интерфейса актуализировать команды установки, запуска и проверок в README, этом файле и CI.
- Для ядра проверять семантику инструкций, флаги, границы, переносы и переходы; для ассемблера — кодирование, метки и диагностику; для системы — обе программы на независимых ожидаемых результатах.
- Для изменений только документации проверять ссылки, соответствие заданию, оформление и `git diff --check`. Помнить, что обычный diff не проверяет ещё не отслеживаемые файлы.
- При значимом изменении обновлять `CHANGELOG.md` в разделе `Unreleased`. Планы хранить в README или задачах, не записывать их как выполненные возможности.
- Не переоформлять посторонние файлы и не добавлять зависимости без потребности текущей задачи.
- В результате работы кратко сообщать, что изменено, что проверено и что осталось неопределённым. Не выдавать локальные проверки за успешный запуск GitHub Actions.

## Известные неопределённости

Таблица вариантов повреждена конвертацией; для № 8 расходится знаковость, у № 16 особая комбинация задач и памяти. Есть расхождения в описании первого элемента массива и условного перехода `JNZ` в стековом примере. Не переносить неоднозначность в код молча: уточнить требование или явно оформить допущение. Состав бригады из трёх человек требует согласования с преподавателем по тексту задания.
