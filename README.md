# Emulator — учебный эмулятор процессора

Практическая работа по дисциплине «Разработка программно-аппаратного обеспечения информационных и автоматизированных систем». Нужно разработать эмулятор процессора, показать исполнение программ по командам и подготовить отчёт.

**Назначен вариант 7:** трёхадресная система команд, гарвардская архитектура, знаковые целые числа в дополнительном коде. Первая программа вычисляет сумму элементов массива, вторая — свёртку двух массивов по 10 элементов с длинной арифметикой.

**Статус:** этап 3 завершён — реализовано ядро CPU на TypeScript: 17 команд, раздельная память, арифметика и флаги, пошаговое исполнение, загрузка и сброс. Есть тесты и запускаемый машинный пример. Ассемблер и браузерный интерфейс React + Vite будут добавлены на следующих этапах.

## Запустить ядро

Нужен Node.js 22 или новее. Команды выполняются из корня:

```bash
npm ci
npm run core:demo
```

Демонстрация собирает ядро и исполняет четыре вручную закодированные инструкции: `MOV`, `MOV`, `ADD`, `HALT`. В терминале видны шаги, машинные слова, регистры и `PC`; результат — `R0 = 5`.

| Команда | Назначение |
| --- | --- |
| `npm run typecheck` | Строгая проверка типов исходников и тестов. |
| `npm test` | Тесты кодека, АЛУ и процессора. |
| `npm run build` | Сборка ядра в `dist/`. |
| `npm run core:demo` | Сборка и запуск примера `examples/machine/add.mjs`. |
| `npm run docs:dev` | Локальная разработка сайта документации. |
| `npm run docs:build` | Сборка сайта для публикации. |
| `npm run docs:preview` | Просмотр собранного сайта. |
| `npm run check` | Проверка типов, тесты, сборка ядра и сайта. |

Подключение ядра, формат образа, снимки и ошибки описаны в [API](docs/architecture/core-api.md). Эти команды позволяют работать с ядром; графического интерфейса пока нет.

## Что требуется по заданию

| Область | Обязательный результат |
| --- | --- |
| Модель процессора | Архитектура памяти и адресность команд по своему варианту; существующая или собственная система команд. |
| Состояние на экране | Регистры общего назначения, включая аккумулятор и счётчик, счётчик команд `PC`, регистр команд `IR`, необходимые флаги. Для безадресной машины — регистровый стек и его указатель вместо РОН. |
| Текущая команда | Машинный код, ассемблерное представление и отдельные поля инструкции. |
| ОЗУ | Хранение программы и массивов; отображение всей памяти необязательно. Методичка рекомендует ограничиться несколькими тысячами ячеек. |
| Исполнение | Обновление и отображение состояния после каждой команды. |
| Система команд | Фиксированная длина инструкций, скалярные операции; к ОЗУ обращаются только команды пересылки и обмена. |
| Адресация | Для адресных машин: непосредственная, прямая, регистровая, косвенно-регистровая. Для стековой — чтение и запись памяти через адрес на вершине стека; остальные способы можно не реализовывать. |
| Набор операций | Пересылка, арифметика и логика, длинная арифметика, условные переходы; достаточно операций, необходимых для двух программ. |
| Ввод программы | Пользователь вводит ассемблер, эмулятор переводит его в машинные инструкции и записывает в память команд. |
| Две программы | Обработка массивов в цикле: сумма элементов массива; затем свёртка двух массивов по 10 знаковых элементов с обязательной длинной арифметикой. |
| Отчёт | Титульный лист, лист задания, описание компонентов и команд, обе программы на ассемблере и в машинном коде, заключение. |

В методичке «свёрткой» названа сумма попарных произведений: `S = A₁ × B₁ + … + Aₙ × Bₙ`. Это один результат, а не массив результатов со сдвигом одного массива относительно другого.

Рабочее представление массива: `[N, x₁, …, xₙ]`, где `N` — число следующих элементов. Длину читаем из памяти; цикл выполняет сам эмулируемый процессор. Прямой расчёт результата средствами языка реализации допустим как эталон проверки, но не заменяет исполнение программы.

## Основные идеи реализации

### Сначала спецификация и две программы

Для назначенного варианта 7 принята [спецификация](docs/architecture/cpu.md): 16 регистров по 16 бит, 1024 инструкции по 32 бита и 4096 слов данных по 16 бит. Определены форматы команд, адресация, флаги и ошибки. [Черновики программ](docs/architecture/programs.md) показывают циклы суммы и свёртки с переносами между словами. Реализовывать все 16 вариантов не требуется.

Для варианта 7 особенно важно различать адресные пространства команд и данных, явно кодировать получателя и два источника, проверять знаковое расширение и переносы при накоплении длинного результата. Предлагаем взять 10 элементов для суммы; для свёртки вариант задаёт два массива по 10 элементов. Подробности — в [разборе вариантов](docs/reference/variants.md).

### Отделить ядро от интерфейса

Разделение модулей: ядро, загрузчик и кодек реализованы, ассемблер и интерфейс добавляются следующими этапами:

```text
Текст программы → Ассемблер → Машинные слова → Загрузчик → Память команд
                                                           ↓
Память данных ↔                                          Ядро CPU
                                                           ↓
                                                Состояние и трасса шага
                                                           ↓
                                                       Интерфейс
```

- **Описание системы команд:** коды операций, поля, допустимые операнды, влияние на флаги. Его используют ассемблер, декодер и отображение команды.
- **Ядро:** раздельная память, регистры, АЛУ и операция `step()` — выполнение ровно одной инструкции. Ядро не зависит от UI.
- **Ассемблер:** разбор строк, проверка операндов, таблица меток, кодирование. Два прохода позволяют разрешать переходы вперёд. Ошибки содержат номер строки и объяснение.
- **Интерфейс:** редактор, кнопки «Собрать», «Шаг», «Запуск», «Пауза», «Сброс», состояние CPU и подсветка изменений. Непрерывное выполнение строится поверх того же `step()` с лимитом команд.
- **Примеры и проверки:** исходники двух программ, исходные данные, ожидаемые результаты и проверка машинного представления.

Ядро должно декодировать машинные слова из памяти: исполнение исходных строк ассемблера напрямую не показывает требуемый цикл работы процессора.

### Сделать арифметику наблюдаемой

Данные имеют ширину 16 бит, инструкции — 32 бита. Вариант 7 использует знаковые числа в дополнительном коде: явно учитывать разрядность, знаковое расширение и различие переноса `CF` и знакового переполнения `OF`. Проверять отрицательные числа, смешанные знаки и минимальное представимое значение.

Длинный результат хранить в нескольких словах, а перенос между словами выполнять командами эмулируемой машины. Даже если одно произведение 16-битных чисел помещается в 32 бита, сумма нескольких таких произведений может не поместиться. Для варианта 7 приняты два 16-битных слова суммы и три слова свёртки, младшее слово хранится по меньшему адресу.

### Выбор технологии

Пользователь выбрал **TypeScript + React + Vite**: ядро и ассемблер — независимые модули TypeScript, интерфейс — браузерное приложение на React. Это позволит демонстрировать приложение в браузере и разделить работу над логикой и визуализацией. Сервер и база данных для базового задания не нужны. Vite предоставляет шаблон `react-ts`: [официальное руководство](https://vite.dev/guide/).

Для точных промежуточных вычислений можно использовать `bigint`, но ограничение разрядности и переносы всё равно моделировать явно. `number` и `bigint` нельзя смешивать в арифметических выражениях без преобразования: [документация TypeScript](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-2.html#bigint). В отчёте нужно показать длинную арифметику самой виртуальной машины.

В ядре промежуточные операции над 16-битными словами точно помещаются в `number`; ограничение разрядности и флаги моделируются явно, независимый эталон в тестах использует `bigint`. Зависимости React и конфигурация приложения Vite появятся вместе с интерфейсом. Стиль SwiftUI используется для оформления сайта, а сам сайт остаётся на VitePress.

## Этапы работы и критерии готовности

1. **Зафиксировать параметры варианта 7.** Вариант и параметры машины определены. С преподавателем остаётся согласовать состав команды и необходимость дополнительной части.
2. **Описать систему команд.** Есть таблица кодирования, правила адресации, флаги и черновики двух программ.
3. **Сделать ядро.** Вручную закодированная программа выполняется по шагам; корректны переходы, границы памяти и остановка.
4. **Добавить ассемблер.** Обрабатываются метки вперёд и назад; неверные команды и операнды дают понятные ошибки; машинные слова совпадают с ручными примерами.
5. **Подключить интерфейс.** Видны обязательные компоненты, поля текущей команды и изменения после шага; запуск можно остановить.
6. **Проверить обе программы.** Массивы обрабатываются циклом; проверены граничные числа, переносы между словами и результаты относительно независимого эталона.
7. **Подготовить защиту.** Отчёт соответствует реализации, содержит оба листинга в двух представлениях; демонстрация воспроизводится на согласованных данных.

Распределение на троих: первый разработчик — ядро и арифметика; второй — ассемблер и программы; третий — интерфейс и интеграция. Спецификацию согласуют все, каждый описывает свой модуль в отчёте. Первый общий результат — сборка и пошаговый запуск маленькой программы через UI.

## Что нужно уточнить

- Методичка предусматривает бригаду из **одного или двух человек**, а нас трое. Нужно согласовать состав и объём работы с преподавателем.
- Размеры и кодирование выбраны как проектные решения в [спецификации](docs/architecture/cpu.md); при дополнительных ограничениях преподавателя контракт потребуется пересмотреть.
- Таблица 4.1 потеряла объединённые ячейки при конвертации. Наше восстановление всех вариантов приведено отдельно и требует сверки с оригиналом.
- Для варианта 8 текст указывает беззнаковые числа, а расположение подписей таблицы допускает попадание в группу знаковой свёртки.
- Первый элемент массива назван то «номером», то длиной. Предлагаем следовать более подробному пояснению: хранить длину.
- Для первого массива встречаются диапазоны 7–15 и 6–15. До уточнения можно взять 10 элементов — это удовлетворяет обоим. Длина массивов свёртки задаётся отдельно вариантом.
- Ссылки на иллюстрации в `task/task.md` ведут в отсутствующий каталог `*_assets`; имеющиеся изображения лежат прямо в `task/`, а `page-04-img-01.png` отсутствует. Исходный материал сохранён без исправлений.

Прерывания, банковая память, конвейеризация и другие расширения из раздела 4.2 обсуждаются после базовой части либо при отдельном требовании преподавателя.

├── task/                     # Исходная методичка и изображения
